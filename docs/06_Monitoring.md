# Monitoring（稼働状況のDiscord通知）

> 状態: 作業計画のみ。実装・実機確認は未実施。

## 1. 目的

サーバーの稼働状況を定期的に確認し、状態が変わったときにDiscordのチャンネルへ通知する。あわせて、デプロイスクリプトの失敗も同じチャンネルへ通知する。

## 2. 構成

```text
タスクスケジューラ（5分ごと）
  → scripts/maintenance/monitor.ps1
      → コンテナの状態を確認（docker inspect の Health）
      → 前回の状態（logs/monitor-state.json）と比較
      → 変化があったときだけ Discord Webhook へ POST
```

| 要素 | 内容 |
|---|---|
| 通知先 | Discordチャンネルの Webhook（Botは使わない） |
| 確認方法 | `docker inspect --format '{{.State.Health.Status}}' cicd-env-satisfactory`。管理用APIの認証は不要 |
| 実行 | Windowsタスクスケジューラ（ユーザーがログオンしているときのみ。`docs/07_Task_Scheduler.md`と同じ方式） |
| 状態の保存 | `logs/monitor-state.json`（`logs/`はGit管理対象外） |
| 通知のタイミング | 状態が変わったときだけ（`healthy`→異常、異常→`healthy`） |

## 3. 方針

- Webhook URLは秘密情報として扱う。`.env`（gitignore）の`DISCORD_WEBHOOK_URL`に置き、リポジトリ、ログ、チャットに書かない。`.env.example`には空の項目だけを追加する
- 異常の判定は、連続3回（約15分）で行う。起動直後のsteamcmdの再起動（`docs/04_Satisfactory_Server.md`の「初回起動で確認した事項」）や、デプロイによる再作成で、誤って通知しないため
- デプロイの実行中（`logs/deploy.log`の最終行が「デプロイ終了」でない間）は、通知を保留する案を検討する
- Webhookの送信に失敗しても、監視自体は止めない（ログに記録する）
- PCがスリープ・停止中は、確認も通知もできない。PCごと止まった場合の検知は、このスクリプトでは対応しない（課題）

## 4. 作業計画

| No. | 作業 | 内容 | 完了の条件 | 実機への影響 |
|---|---|---|---|---|
| 1 | Webhookの作成（ユーザー） | Discordのチャンネル設定から、通知用のWebhookを作成する。URLは`.env`の`DISCORD_WEBHOOK_URL`に、ユーザーが自分で設定する（チャットに貼らない） | `.env`に項目がある | なし |
| 2 | `.env.example`の更新 | `DISCORD_WEBHOOK_URL=`（空）を追加する | 項目が追記されている | なし |
| 3 | `monitor.ps1`の作成 | 状態の取得、前回との比較、連続失敗の数え上げ、Discordへの送信、状態ファイルの更新を実装する。PowerShell 5.1向け、BOM付きUTF-8 | 構文エラーがない | なし（作るだけ） |
| 4 | 送信のテスト | 引数（例: `-Test`）で、テストメッセージを1件送る。**外部サービスへの送信にあたるため、実行前にユーザーの確認を取る** | チャンネルにテストメッセージが届く | Discordへの送信のみ |
| 5 | 状態遷移の確認 | 状態ファイルを書き換えた模擬の状態で、通知の有無と回数を確認する（コンテナは止めない） | 変化時だけ通知される | なし |
| 6 | 異常時の確認（任意） | コンテナを一時的に止めて、異常通知と復旧通知を確認する。**稼働中のサーバーを止めるため、プレイしていない時間帯にユーザーの確認を取ってから行う** | 異常と復旧の通知が1回ずつ届く | 一時停止あり |
| 7 | デプロイ失敗の通知 | `deploy.ps1`の失敗時に、`monitor.ps1`の送信関数（またはWebhook送信の共通処理）を呼ぶ | 失敗時に通知が届く | なし |
| 8 | タスクの登録 | 5分ごとに実行するタスク（`CICD-ENV Monitor`）を登録する。登録はユーザーが行う | `LastTaskResult`が`0` | なし |
| 9 | ドキュメントの更新 | この文書の「状態」を更新し、確認結果を記録する。`docs/07`にタスクの登録手順を追記する | 反映済み | なし |

## 5. 未確認事項と判断待ち

| No. | 項目 | 状態 |
|---|---|---|
| 1 | 確認の間隔と、異常とみなす連続回数 | 案: 5分間隔、連続3回。運用しながら調整する |
| 2 | 通知の内容 | 案: サーバー名、状態、時刻、前回からの経過時間。プレイヤー数などは、認証が必要なため含めない |
| 3 | 通知のメンション | 案: なし。必要ならユーザーIDやロールを指定する |
| 4 | 定期的な生存通知（例: 1日1回） | 案: なし。PCごと止まった場合の検知に使える |
| 5 | 管理用APIでの確認（`HealthCheck`はHTTPS・認証不要） | 案: `docker inspect`で十分だが、ポートの疎通も確認したい場合は`HealthCheck`の追加を検討する |
| 6 | PC・ネットワークごと止まった場合の検知 | 未対応。外部の死活監視サービスが必要になる |
