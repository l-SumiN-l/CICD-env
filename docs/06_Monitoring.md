# Monitoring（稼働状況のDiscord通知）

> 状態: `monitor.ps1`、送信処理、デプロイ失敗の通知、毎時の定期通知を実装済み。DryRunによる状態遷移の確認、Discordへのテスト送信、デプロイ失敗通知の実機確認まで完了。タスクの登録（手順は`docs/07`の9）と、異常時の実機確認は未実施。進捗は「6. 実装状況」を参照。

## 1. 目的

サーバーの稼働状況を定期的に確認し、状態が変わったときにDiscordのチャンネルへ通知する。あわせて、デプロイスクリプトの失敗も同じチャンネルへ通知する。

## 2. 構成

```text
タスクスケジューラ（5分ごと）
  → scripts/maintenance/monitor.ps1
      → コンテナの状態を確認（docker inspect の Health）
      → 前回の状態（logs/monitor-state.json）と比較
      → 変化があったときだけ Discord Webhook へ POST
```

| 要素 | 内容 |
|---|---|
| 通知先 | Discordチャンネルの Webhook（Botは使わない） |
| 確認方法 | `docker inspect --format '{{.State.Health.Status}}' cicd-env-satisfactory`。管理用APIの認証は不要 |
| 実行 | Windowsタスクスケジューラ（ユーザーがログオンしているときのみ。`docs/07_Task_Scheduler.md`と同じ方式） |
| 状態の保存 | `logs/monitor-state.json`（`logs/`はGit管理対象外） |
| 通知のタイミング | 状態が変わったとき（`healthy`→異常、異常→`healthy`）と、1時間に1回の定期通知（正常・異常のどちらでも現在の状態を送る） |

## 3. 方針

- Webhook URLは秘密情報として扱う。`.env`（gitignore）の`DISCORD_WEBHOOK_URL`に置き、リポジトリ、ログ、チャットに書かない。`.env.example`には空の項目だけを追加する
- 異常の判定は、連続3回（約15分）で行う。起動直後のsteamcmdの再起動（`docs/04_Satisfactory_Server.md`の「初回起動で確認した事項」）や、デプロイによる再作成で、誤って通知しないため
- デプロイの実行中（`logs/deploy.log`の最終行が「デプロイ終了」でない間）は、通知を保留する案を検討する
- Webhookの送信に失敗しても、監視自体は止めない（ログに記録する）
- PCがスリープ・停止中は、確認も通知もできない。PCごと止まった場合の検知は、このスクリプトでは対応しない（課題）

### 実装の補足

- 通知の判定は、`docker inspect`の`Health.Status`が`healthy`かどうかで行う。Dockerが止まっている場合やコンテナがない場合は、`unavailable`として異常に数える
- コンテナが`healthy`のときは、さらにPCのLAN側のIPv4アドレス（既定ゲートウェイを持つ有効なアダプター。WSL・Dockerの仮想アダプターは除く）経由で`https://<IP>:<SATISFACTORY_GAME_PORT>/api/v1`に`HealthCheck`を送る。応答がなければ「LAN経由の応答なし」として異常に数える。自己署名の証明書を受け入れる設定は、この呼び出しの間だけ有効にする
- LAN側のIPが前回と変わったときだけ、1回通知する。IPの値は、通知にもログにも出さない（前回のIPは`logs/monitor-state.json`に保存する）。通知の送信に失敗したら、次の実行で再試行する
- PC自身から自分のIPへの接続は、Windowsのファイアウォールを通らない。そのため、ファイアウォールの設定ミスは検知できない
- 連続3回の異常で1回だけ通知し、復旧したときに復旧の通知（停止していた時間つき）を送る
- 定期通知は、`yyyy-MM-dd HH`が前回の通知と違う最初の実行で送る（毎時0分ごろ）。正常なら「稼働中」、異常なら状態と連続回数（連続3回以降は「停止中」と停止からの経過時間）を送る。異常・復旧の通知を送った回は、定期通知を重ねない。送信に失敗したら、次の実行で再試行する。そのため、タスクの登録直後の最初の実行でも1件届く
- `deploy.ps1`は、失敗時の通知のログを書いたあとで`--- デプロイ中止 ---`を最終行に書く（以前は順序が逆で、`monitor.ps1`が中止後の30分間をデプロイの実行中と誤認してスキップした。2026-10-24に修正）
- `logs/deploy.log`の最終行が「デプロイ終了」「デプロイ中止」のどちらでもなく、30分以内に更新されている間（デプロイの実行中）は、確認をスキップする
- Webhook URLは`.env`から読み、ログや画面に出さない。送信の失敗は、HTTPのステータスのみをログに残す
- ログは`logs/monitor.log`、状態は`logs/monitor-state.json`（どちらもGit管理対象外）

## 7. 今後見直す課題（サーバーの稼働状況の検知）

2026-10-25に、毎日09:00（UTC 00:00）のゲームのセッション再起動で切断され、その後に再接続できない事象があった。コンテナは`healthy`のままで、毎時の定期通知も「稼働中」のままだった（コンテナ内側の`HealthCheck`しか見ていなかったため）。サーバー側にクラッシュなどの異常は見つからず、ゲームのクライアントを再起動して接続し直したところ、接続できた。原因は未確定（クライアント側が再起動前の接続状態のまま再試行を続けていた可能性が高い）。

このうち、LAN側のIP経由の`HealthCheck`とIP変更の通知は実装した（6のNo.11）。次の項目は対象外とし、課題として残す。

| No. | 課題 | 内容・制約 |
|---|---|---|
| 1 | 再起動の開始と完了の通知 | コンテナの再起動（デプロイ、手動）と、ゲームの毎日のセッション再起動（ログの`Session Restart Timer elapsed`）の開始・完了をDiscordへ通知する。完了を示すログの行は未確認。`starting`が長く続く場合（起動後のゲーム本体の検証に約9分かかった）を異常にするかも未決 |
| 2 | 再起動前のプレイヤーへのアナウンス | 公式のAPIに、チャットやアナウンスの機能はない（`RunCommand`は管理者のトークンが必要で、アナウンスのコマンドは未確認）。毎日のセッション再起動は、ゲーム自身が行うため、外から止めたり予告したりできない |
| 3 | 接続中のプレイヤーの確認 | `QueryServerState`の接続人数には、トークンが必要。トークンの保管方法が未決（`docs/05_Backup.md`の11のNo.5と同じ課題）。トークンなしでは、ゲームのログからの推定のみ（精度が落ちる）。再起動を伴うデプロイを、プレイ中に実行しない制御にも使える |
| 4 | ゲームに接続できるかの確認 | `HealthCheck`はゲームのクライアントの接続を保証しない。クライアントの接続（UDP）そのものは、PC自身からは確認できない。再起動後に一定時間ログインがないことを、ログから知らせる案がある |
| 5 | ファイアウォールの設定ミスの検知 | PC自身から自分のIPへの接続は、ファイアウォールを通らないため、検知できない。別の端末からの確認が必要 |
| 6 | 毎日のセッション再起動の時刻 | 設定で変えられる可能性があるが、設定名と変更方法は未確認（管理用のAPIかゲーム内の設定） |
| 7 | 起動のたびにゲーム本体を検証する | `SKIPUPDATE=false`のため、起動後の約9分は接続できない。タグの固定と`SKIPUPDATE`の方針（`docs/04_Satisfactory_Server.md`の課題）と合わせて検討する |
