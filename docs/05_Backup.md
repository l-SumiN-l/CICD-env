# Backup Design

## 1. 目的と方針

セーブデータを失わないことを最優先にする。README の方針に従い、次を満たす。

- セーブデータ、サーバー設定、Docker Compose設定を対象にする
- 定期、更新前、手動の3つのタイミングで取得する
- 世代管理する
- 「更新前にバックアップを取り、失敗したら更新しない」
- 原則無料のツールだけで構成する
- **PCの突然の停止（電源断、強制再起動、ブルースクリーン）を想定して設計する**

このドキュメントは設計である。スクリプトは、設計の確認後に作成する（「10. 実装の順序」を参照）。

## 2. 現状の確認結果（2026-10-18）

| 項目 | 確認結果 |
|---|---|
| `data/satisfactory/saved` のサイズ | 約2.4MB |
| `data/satisfactory/gamefiles` のサイズ | 約2.7GB（再ダウンロードで復元できる） |
| オートセーブ | `saved/server` に5世代がローテーションする。ファイルの更新間隔は15分だった（観測値）。ゲーム内の設定値は未確認 |
| イメージ側のバックアップ | コンテナの起動時に、セーブを `data/satisfactory/backups` へコピーする。取得は起動時のみで、定期的には取得しない |
| 停止時のセーブ | コンテナの停止は約1秒で終わり、停止時にセーブした形跡はない |
| 保存先のディスク | C: ドライブのみ（空き約102GB、NTFS）。別ドライブはない |
| PCの種別 | バッテリーあり（ノートPC）。停電時はバッテリーで動作する |
| Docker Desktop の再起動 | 手動で終了して起動し直すと、コンテナは自動復旧しない。PCを再起動すると自動復旧した（2026-10-18確認） |

## 3. 想定する障害と対策

| No. | 障害 | 起きること | 対策 |
|---|---|---|---|
| 1 | PCの突然の停止 | 書き込み中のセーブが壊れる。直近のオートセーブ（最大15分分）が失われる | オートセーブ5世代を一次防御にする。バックアップは書き込みが終わったファイルだけを取得し、検証する。作業は一時フォルダで行い、完成してから確定する（5.2を参照） |
| 2 | バックアップ処理中のPC停止 | 中途半端なバックアップが残る | 一時フォルダで作成し、完了後に名前を変更して確定する。確定前のものは、次回に削除する |
| 3 | ディスクやPCの故障 | `data/` とバックアップが同時に失われる | **現時点では対策しない**（同じディスクに保存するため。6を参照）。将来、別の媒体へのコピーを追加する |
| 4 | 誤操作（`down -v`、`data/` の削除） | セーブデータの消失 | 世代バックアップから復元する |
| 5 | ゲーム更新によるワールドの破損 | 起動できない、またはセーブを読めない | 更新前にバックアップを取る。失敗したら更新しない |
| 6 | バックアップ時刻にPCが停止中 | 取得の漏れ | タスクの `StartWhenAvailable` と、ログオン時の実行で補う |
| 7 | バックアップの失敗に気づかない | 古いバックアップしか残っていない | ログと最終成功時刻を確認する。通知は `docs/06_Monitoring.md` で扱う |

### 突然のPC停止について

次のことを前提にする。

- セーブファイルは、書き込み中に電源が落ちると壊れる可能性がある。壊れたセーブは、コピーしても壊れたままである
- そのため、最新のセーブだけに頼らない。「オートセーブ5世代」と「バックアップの世代」の両方に、過去のセーブが残る形にする
- バックアップは、取得時にファイルが更新中でないことを確認する
- Windows Updateの自動再起動も、突然の停止の原因になる。設定の変更は、ライセンス上の制約により難しいため、停止は起きるものとして備える
- 復旧後の確認手順は「8. PC停止後の確認手順」にまとめる

## 4. バックアップの対象

| 対象 | 取得 | 理由 |
|---|---|---|
| `data/satisfactory/saved/` | する | セーブデータ、サーバー設定（`ServerSettings.7777.sav`）、ブループリント |
| `.env` | する | Gitに含まれない。現在は秘密情報を含まないが、含める場合は保存先を見直す |
| `compose/`、`.env.example`、`docs/` | しない | Gitで管理している |
| `data/satisfactory/gamefiles/` | しない | 約2.7GBあり、`steamcmd` で再取得できる |
| `data/satisfactory/backups/` | しない | イメージが起動時に作る。補助的な保険として残す |
| `logs/` | しない | 調査時に必要な分だけ別途保存する |
| `.mcp.json` | しない | 個人設定で、トークンの参照を含む |

## 5. 取得の方法

### 5.1 取得のタイミング

| 種別 | タイミング | 備考 |
|---|---|---|
| 定期 | 1時間ごと | オートセーブ（15分）の4回に1回取得する。前回から `saved` の内容が変わっていなければ、取得しない |
| 更新前 | デプロイ（`docker compose up -d`）の直前 | 失敗したらデプロイを中止する（`docs/07_Task_Scheduler.md` と連携する） |
| 手動 | 必要なとき | メンテナンスの前など |
| 復旧時 | ログオン時 | PCの停止後に、取得の漏れを補う |

### 5.2 手順

1. 前提を確認する（`saved` が存在する、保存先に十分な空きがある）
2. 対象ファイルが、最後の更新から60秒以上経過していることを確認する。経過していなければ待ち、最大5回まで再試行する
3. `<保存先>\_tmp\<日時>\` に、`saved/` をコピーする（`<保存先>` は、6の保存先）
4. コピー後に、すべてのファイルのサイズとSHA256を、元のファイルと比較する。コピー中に元のファイルが更新されていれば、手順2からやり直す
5. `manifest.json` を作成する（ファイル名、サイズ、SHA256、取得時刻、取得の種別、イメージのタグ）
6. 一時フォルダの名前を `<保存先>\<種別>\<日時>\` に変更して確定する
7. 世代の整理を行う。**手順1〜6がすべて成功した場合だけ**行う

形式は、サイズが小さいため、圧縮しないフォルダにする。確認と復元が簡単になる。保存先はリポジトリの外にあるため、`.gitignore` の対象外である。

## 6. 保存先

保存先は、**ローカルの別フォルダ**とする（2026-10-19決定）。

| 項目 | 内容 |
|---|---|
| 保存先 | `C:\CICD-env-backup\`（案。実装時に確定する） |
| 場所 | **リポジトリのフォルダの外**にする |
| 外部の媒体への保存 | 行わない（個人のデータを、会社のアカウントの同期先などへ置けないため）。ライセンス上の制約も、確認済みである |

### リポジトリの外に置く理由

- `git clean -fdx` やリポジトリのフォルダの削除で、除外対象のファイル（`data/` と、リポジトリ内の `backup/`）が一緒に消えるため
- バックアップのフォルダを、リポジトリの作業とは切り離しておくため

### この構成で守れるもの、守れないもの

| 障害 | 守れるか |
|---|---|
| PCの突然の停止（セーブの破損） | 守れる（世代と検証による） |
| 誤操作（`down -v`、`data/` の削除） | 守れる |
| ゲーム更新によるワールドの破損 | 守れる |
| ディスクやPCの故障 | **守れない**（同じディスクに保存するため） |

ディスクやPCの故障に備える場合は、あとから別の媒体へのコピーを追加する。外付けのドライブなどが候補になるが、現時点では採用しない。

## 7. 世代管理

| 種別 | 保持 | 目安のサイズ（2.4MB／回） |
|---|---|---|
| 定期（1時間ごと） | 直近10世代 | 約24MB |
| 更新前 | 10世代（案） | 約24MB |
| 合計 | | 約48MB |

2026-10-19の決定: 定期は「1時間ごとに、直近10世代」とする。

- 更新前の世代は、定期の整理の対象外にする
- 世代の整理は、バックアップの成功後にだけ行う
- `saved` が大きくなった場合は、保持する世代数を見直す
- 前回から `saved` の内容が変わっていなければ取得しないため、誰もプレイしていない間は、世代が増えない。その間は、より長い期間の世代が残る

### 注意

プレイ中に1時間ごとに取得すると、10世代で約10時間分の履歴になる。**10時間以上前の状態へ戻したい場合（例: 翌日になって、ワールドの異常に気づいた場合）は、復元できない。**

日次の世代を追加する案（7世代、約17MB）は、**採用しない**（2026-10-19決定。バックアップの稼働は、それほど重要ではないため）。課題として「11. 未確認事項と判断待ち」に残す。

## 8. PC停止後の確認手順

PCが突然停止して、再起動した後に実施する。

| 手順 | 確認内容 |
|---|---|
| 1 | Windowsにログオンし、Docker Desktop が起動するのを待つ。コンテナは、PCの再起動後は自動で復旧する（2026-10-18確認）。Docker Desktop だけを終了した場合は、自動では復旧しない |
| 2 | `docker compose --env-file .env -f compose/docker-compose.yml ps` で、`healthy` になっているか確認する |
| 3 | ゲームクライアントから接続し、ワールドが読み込めるか確認する |
| 4 | 進捗が大きく巻き戻っている、またはワールドが読み込めない場合は、`saved/server` のほかのオートセーブ（`_autosave_0` 〜 `_autosave_4`）を試す |
| 5 | それでも復旧できない場合は、バックアップから復元する（9を参照） |
| 6 | ファイルシステムの異常が疑われる場合は、`chkdsk` の結果を確認する |

## 9. 復元の手順（概要）

復元スクリプトは、バックアップの取得が安定してから作成する。手動で行う場合の流れは次のとおり。

1. `docker compose --env-file .env -f compose/docker-compose.yml stop` でサーバーを停止する
2. **現在の `saved/` を削除せず、名前を変更して退避する**（例: `saved.broken-<日時>`）
3. 復元する世代の `saved/` を、`data/satisfactory/saved/` にコピーする。`manifest.json` のSHA256で、整合性を確認する
4. `docker compose --env-file .env -f compose/docker-compose.yml up -d` で起動する
5. ゲームクライアントから接続して、ワールドを確認する

`down -v` と、`data/` 配下の削除は、使わない。

### 復元テスト

- 初回に、別のフォルダへ復元して、内容を確認する
- 以降は、月に1回実施する
- 実際のサーバーでの復元は、メンテナンスの時間に行う

## 10. 実装の順序

| フェーズ | 内容 | 前提 |
|---|---|---|
| 1 | 手動のバックアップと復元の手順を確認する（本ドキュメントの5.2と9を、手で実行する） | このドキュメントの確認 |
| 2 | バックアップスクリプト（`scripts/backup/`）とタスクの作成 | フェーズ1の完了 |
| 3 | 更新前のバックアップを、デプロイスクリプトへ組み込む | フェーズ2の完了 |
| 4 | 別の媒体へのコピーの追加（任意） | 使える媒体が決まったとき |
| 5 | 失敗の検知と通知（`docs/06_Monitoring.md`） | フェーズ2の完了 |
| 6 | 復元スクリプトと、復元テスト | フェーズ2の完了 |
